# TRIP-007 Import the course data: solution

How it is built. What is built and why (goal, scope, requirements) is in the card: `gh issue view 11`.

## Data

Two new migrations. The data is a generated SQL migration, as for the routes, so it is versioned, runs once per database and is the same locally and on Turso (settled 2026-10-20):

- `db/migrations/005_charter.sql`: the tables.
- `db/migrations/006_charter_data.sql`: the data, generated by `scripts/generate-charter-data.mjs`.

New tables, as built (described for developers in `wiki/system/data-charter.md`):

| Table | One row per | Main columns |
|---|---|---|
| `charter_airports` | charter airport | `iata` (key), `name`, `city`, `country`, `country_name`, `latitude`, `longitude`, `timezone` |
| `destinations` | destination | `id` (key, e.g. `teufelsberg`), `title`, `description`, `continent`, `country`, `country_name`, `region`, `locality`, `category`, `access`, `nearest_airport` → `charter_airports`, `nearest_distance_km` (or null), `gateway_airport` → `charter_airports` or null, `status_checked`, `status_source`, `path` |
| `destination_aliases`, `destination_tags`, `destination_transport` | alias, tag or way of getting there | `destination_id`, `position`, the value |
| `destination_pages` | destination | `destination_id` (key), `overview`, `getting_there`, `visiting` (Markdown) |
| `destination_photos` | destination with a photo | `destination_id` (key), `src`, `author`, `license`, `license_url`, `source` |
| `charter_timetables` | timetable | `id` (key, e.g. `ARN-BER-EW488`), `airline`, `from_airport`, `to_airport` → `charter_airports`, `valid_from`, `valid_to`, `departs`, `arrives`, `arrival_day`, `duration_minutes`, `price` (kr) |
| `charter_timetable_days` | weekday of a timetable | `timetable_id`, `weekday` (`Mon` … `Sun`) |
| `charter_timetable_flights` | leg of a timetable | `timetable_id`, `position`, `flight_number` |
| `charter_timetable_stops` | change airport of a timetable | `timetable_id`, `position`, `airport` → `charter_airports` |

Dates are stored as `YYYY-MM-DD` and times as `HH:MM`, as in the course data and in `route_departures`. The rules of R7 are `NOT NULL`, `REFERENCES`, `CHECK` and primary keys in `005_charter.sql`; an index on `charter_timetables (from_airport, to_airport)` serves the later charter search.

## Interface

No visible change.

- `scripts/generate-charter-data.mjs` (new): reads `data/` and `knowledge/`, writes the data migration.
- `lib/travel.ts`: reads the destinations from the database.
- `app/api/destinations/route.ts`: unchanged response, now `async`.
- `tests/helpers.ts`: `queryTestDb` reads the local test database; it replaces the copy TRIP-005's tests had of their own.
- `tests/TRIP-007-import-course-data.spec.ts` (new).

## Decisions

- **The data check missed one thing:** Grytviken and Whalers Bay (Antarctica) have no distance to their nearest airport (`distance_km: null`), because the only way there is a long sea voyage. The course format documents this (`knowledge/index.md`), and R2 doesn't require a distance, so `nearest_distance_km` may be null.
- **The destinations come from `data/destinations.json`, the text and `status_source` from the pages.** The check showed their frontmatter is identical, so reading the facts from one place keeps the script short; only what is on the pages alone is read from them.
- **`GET /api/destinations` builds the same JSON as the file,** from five queries run in parallel (destinations with their airports, aliases, tags, transport, photos), so the response is unchanged and fast.
- **Foreign keys are only checked locally.** SQLite checks `REFERENCES` only when the connection turns it on; the site and `db-setup.mjs` do so for local files. The data migration is generated from read-only files and runs first in CI's test database, so a broken reference is caught there before it reaches Turso.
